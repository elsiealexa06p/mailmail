Ref-Parameter pro Empfänger

{% if cfg.redirect_append_ref %} AN — jeder Redirect-Link wird beim Versand umgeschrieben. {% else %} AUS — Links werden unverändert verschickt. {% endif %}
Beispiel: https://share.google/abc123 → https://share.google/abc123?ref=amFuZUBleGFtcGxlLmRl. Die Empfänger-E-Mail wird base64url-codiert — nie im Klartext in URLs, CDN-Logs oder Browser-History sichtbar. Dekodieren: echo amFuZUBleGFtcGxlLmRl | base64 -d → jane@example.de. Nutzt &ref=, falls der Link bereits einen Query-String hat. Funktioniert mit S3- und Google-Share-Links.

Für jede Ziel-URL wird 1 (oder N) share.google-Link erzeugt. Jeder Link zeigt bei Klick auf sein spezifisches Target — perfekt wenn du mehrere Kunden/Kampagnen parallel bespielst und Traffic- Zuordnung willst.

Redirects generieren (Google /goto) experimentell

Nutzt Googles signed open-redirect www.google.com/goto?url=<token>. Kein Suchmaschinen-Interstitial, direkte Weiterleitung.
⚠ TTL 1-3 Tage (Google entscheidet, Token ist signiert). Kurz vor Kampagnenstart generieren. Bei größeren Batches: Proxy-Pool nutzen, sonst rate-limit'et Google nach ~50-100 Requests.
Methode: URL wird als Google-Suche geschickt, das /goto?url= aus der SERP extrahiert — Bruch möglich wenn Google das UI ändert.

Google rate-limitet ab ~10 parallelen Requests je IP.
Playwright braucht Chromium installiert: pip install playwright && playwright install chromium. ~3-5s pro Link, aber führt JS aus wie ein echter Browser. Requests ist schnell (~300ms) aber Google mappt uns aggressiv auf die JS-only SERP → meist kein Token.
⚠ Proxy-Auth: Chromium supported kein SOCKS5 mit Auth (bekannter Bug). Was funktioniert: http://user:pass@host:port (HTTP-Proxy mit Auth) ODER socks5://host:port (SOCKS ohne Auth). Bei SOCKS5+Auth wird der Proxy still übersprungen, du siehst das im Test-Status.
Testet die erste URL aus der Textarea, zeigt HTTP-Status + HTML-Snippet.
